# S21 case: kpatch-build v0.9.10 binds the wrong `pwq_cache` in CVE-2026-43074 (8 Oct 2026)

**Found by:** S21 sweep scoring (`lab/s12/s21oracle.py`, set v0.9.10 gcc-13, output `/opt/atlas/s12/oracle/s21-v0.9.10-gcc-13.json`), 21:00 UTC 8 Oct. Oracle v1 and v1.1 both report sympos DIVERGENT for 6.6/CVE-2026-43074; v1.1 overall DIVERGENT (multiset and sequence CONSISTENT), the only v1.1 alarm among the 93 v0.9.10 modules. Controls passed (wrong-reference NO_COMMON_FUNCTIONS; no-op byte-identical, same verdict).

## The fault

- Fix: CVE-2026-43074, `fs/eventpoll.c` (adds an `rcu_head` to `struct eventpoll` and frees it with `kfree_rcu`), 6.6.47 pin, gcc 13.3.0 (Ubuntu build).
- `vmlinux` of the pin has two local `pwq_cache` objects:

| kallsyms position (address order) | address | file | symbol-table index |
| ---: | --- | --- | ---: |
| 1 | `ffffffff830a3880` | `eventpoll.c` | 22249 |
| 2 | `ffffffff83cc86e0` | `workqueue.c` | 7953 |

- v0.9.11 module: `.klp.sym.vmlinux.pwq_cache,1` (eventpoll's copy): correct.
- v0.9.10 module: `.klp.sym.vmlinux.pwq_cache,2` (workqueue's copy): **wrong entity**. The position follows symbol-table order, where workqueue's copy comes first. This is the defect fixed by kpatch commit `c608faf` (between v0.9.10 and v0.9.11), which its message ties to gcc 14; here it occurs with gcc 13.
- The reference is in `.klp.rela.vmlinux..text.ep_clear_and_put` at offset `0xb0`: the replaced `ep_clear_and_put` frees `eppoll_entry` objects with `kmem_cache_free(pwq_cache, ...)`. The objects are allocated by `ep_ptable_queue_proc`, which the module does not replace, from eventpoll's cache.
- The only other v0.9.10 vs v0.9.11 difference in `.klp.sym` symbols over all 93 common fixes: 6.12/CVE-2025-38643, where v0.9.10 binds two existing `__already_done` WARN_ONCE flags that v0.9.11 does not reference; the sympos check finds both copies in the right source file (CONSISTENT).

## Runtime consequence (`case-43074.sh`, runtime host, 6.6.47 pin, `slub_debug=F`)

Static test program `epoll-free.c`: 64 rounds of `epoll_create1`, `epoll_ctl(ADD)` on a pipe, `close`. Three arms, three runs each:

| Arm | Module SHA-256 | Enabled, transition | "Wrong slab cache" warnings per run | Test completed |
| --- | --- | --- | --- | --- |
| No module | n/a | n/a | 0, 0, 0 | 3/3 |
| v0.9.11 module | `19fa5c6a...2e6c` | 1, 0 | 0, 0, 0 | 3/3 |
| v0.9.10 module | `26bcb769...e5cf` | 1, 0 | 128, 128, 128 | 3/3 |

Kernel message (v0.9.10, every free): `cache_from_obj: Wrong slab cache. kmalloc-512 but object is from kmalloc-64`, followed by `WARNING: ... at mm/slab.h:661 kmem_cache_free`. Both caches are merged into kmalloc caches on this configuration (`CONFIG_SLAB_MERGE_DEFAULT=y`): eventpoll's into kmalloc-64, workqueue's into kmalloc-512. The warning exists only because `slub_debug=F` turns on consistency checks; the pin's default configuration (`CONFIG_SLUB_DEBUG=y` without debug flags, no `CONFIG_SLAB_FREELIST_HARDENED`) does not check, so on a production boot the same frees put 64-byte objects on the kmalloc-512 free list without any message.

Pin bzImage `41e70d71...70ef`; test binary `87497c41...3ecc`. Logs: `case-43074-logs/`; counts: `case-43074-counts-2026-10-08.txt`.

## Reading

A released generator turned a real CVE fix into a module that builds, loads, enables and completes its transition, and then frees eventpoll objects into the wrong slab cache whenever an epoll file with registered waits is closed. Every operator-visible signal says the system is patched. Of the checks run so far, only LPFid's sympos binding check reports it.

## Which kpatch commit fixes it (9 Oct 2026, `attr.sh`)

Both candidate commits between v0.9.10 and v0.9.11 that touch symbol lookup were tested in both directions on the same fix, tree restore and compiler as the campaign:

| Variant | Module SHA-256 (prefix) | Binding |
| --- | --- | --- |
| A v0.9.10 + c608faf "Fix sympos for gcc-14" | 20623ec9 | `pwq_cache,1` (correct) |
| B v0.9.10 + 0f0294a "lookup: fix local bind check" | faa5005a | `pwq_cache,2` (wrong) |
| C v0.9.11 - c608faf | 7e0aebb0 | `pwq_cache,2` (wrong) |
| D v0.9.11 - 0f0294a | a3701a0e | `pwq_cache,1` (correct) |

c608faf alone decides the binding. Its message ties the problem to gcc 14; the pin here was built with gcc 13.3.0 and already lists the two `pwq_cache` copies in symbol-table order different from address order.
