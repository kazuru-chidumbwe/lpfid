# S2: root cause of the 17 mutants oracle v1.1 did not detect (9 Oct 2026)

Source: `s2-s12-fixtures-2026-10-09.json`; checked by hand on the build host with the frozen v1.1 oracle.

1. **16 addend mutants (3 real-fix, CVE-2026-80574 `focaltech_process_byte`; 13 fixture, kpatch `data-new` and `new-globals`, `meminfo_proc_show`).** Each moves an `R_X86_64_32S` reference into a string section by 8 bytes. The oracle compares string targets by their text after rule N3, which replaces a leading `name: ` (the `pr_fmt` module prefix) by `<pfx>: `. Example: parent `.rodata.focaltech_process_byte.str1.8 + 0` = "focaltech: Invalid finger in abs packet: %d\n"; mutant `+ 8` = "h: Invalid finger in abs packet: %d\n". N3 maps both to "<pfx>: Invalid finger ...", so they compare equal. N3 is broader than its purpose: any word followed by ": " at the start of the text is treated as a module prefix. Reported as a limitation of N3; the S15 ablation shows it directly.
2. **1 redirect mutant (CVE-2024-47674, 6.6): an equivalent mutant, not a miss.** The S1 rule redirects every call to `rep_movs_alternative` to `clear_page_rep`; both calls are in `.altinstr_replacement` at offsets 0x72 and 0x8c. The module's `.altinstructions` has four entries, all for `remap_pfn_range_internal`, whose replacement code lies at 0xe3 to 0xf2; no entry points at 0x72 or 0x8c, so the mutated bytes are never patched into any function and never run. (Corrected 9 Oct after reading the `.altinstructions` entries; the first reading called it a scope limit.)

**Correction (oracle v1.2, S16 Deviation 2):** N3 narrowed to the module's own `pr_fmt` prefix (N3M); and the replacement code of every alternative whose instruction lies in a compared function is now compared (ALT), so a fault in replacement code that does run is visible.
