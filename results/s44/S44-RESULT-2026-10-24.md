### The five alarms

All five are `livepatch-CVE-2023-5090`, in `6.1.49-69.116`, `6.1.49-70.116`, `6.1.52-71.125`, `6.1.55-75.123` and
`6.1.59-84.139`, and v2.0 gives the same verdict. Each differs in `svm_set_x2apic_msr_interception` only
(`fa5090-2026-10-25.txt`, `_fa5090.py`). The function loads the end address of `direct_access_msrs`, a 368-byte
(0x170) array in its own section `.rodata.direct_access_msrs`. The module names that address
`.klp.sym.kvm_amd.direct_access_msrs,1+0x170`; the reference names it `.rodata.direct_access_msrs+0x170`, the end of
the section, which no object symbol covers, so the naming rules cannot map it to `direct_access_msrs`. The `+0x8`
reference to the same array maps on both sides. Every other relocation of the function pairs. It is one address
named two ways, not a fault, and it is the S26 development residual (`6.1.56-82.125`, Section 7.6 of the manuscript)
in five further builds of the same fix. The protocol counts it as it falls: 1 alarming fix, 5 modules, 5 functions.
No alarm falls in H-new or on AArch64.

its sha256 was recorded in `~/s44/vmlinux-sha256.txt`. The runner does not return to a scored package. A re-score
that needs the position check decompresses the file and checks it against that record.
